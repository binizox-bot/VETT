# Pilot-10 结果（2026-11-13，本地零成本）

## 设置
- 10 场 closure-clean 比赛，28 个 core 字段，7 个变体。
- 模型：qwen2.5:7b-instruct-q4_K_M、llama3.1:8b（Ollama，本机 RTX 3070）。
- 系统：direct（直接生成）/ closure（Python 按闭合规则重算派生字段）/ guided（prompt 内写规则，无后处理）。
- 解码：temperature=0，seed=20261112，num_ctx=8192，direct/closure 700 tokens，guided 900 tokens。
- 调用：约 620 次本地调用，¥0。

## 五条发现

1. **换序破坏是稳健的。** 两个模型、三个系统下，17%–29% 的“原本正确”字段在纯换序后变错；
   同 prompt 重测的对应比例是 0/294。与 H1 的 14.3% 一致，且跨模型复现。
2. **外部依赖传播显著改善派生字段。** 修订后 changed 字段：direct 0.54/0.62 → closure 0.78/0.89；
   闭合率 0.58/0.68 → 1.00。**注意**：本 pilot 的 revised 恰好改在可被闭合规则重算的字段上，
   所以这部分提升带有“按定义正确”的成分；需要 30 场加入不可由闭合恢复的修订来分离。
3. **prompt 里写规则基本无效，甚至会破坏格式。** qwen guided 与 direct 持平；
   llama guided 63/70 行解析失败。外部机制（closure）有效，提示词机制无效——
   这正好支撑“状态维护需要外部结构，不是提示工程”。
4. **缺证时 100% 编造。** 所有模型、所有系统，missing 变体的 UNKNOWN 正确率都是 0.000；
   模型从不拒答，总是给出一个具体数字。
5. **旧值残留不是这批模型的失败模式。** revised 的 stale rate 为 0–2.7%；
   行内更正（POM 后文改判）后旧值率 0.000，两个模型都采纳了后文更正。
   所以“版本化”在**单次上下文内、显式更正**的场景下它们能做对；
   不能把“旧值残留”当作本数据上的主卖点。

## 配对指标
- 严格整场配对（control 全对 ∧ revised changed 全对 ∧ 未变全对）为 0/10——32 字段全对不现实。
- 改用**字段级配对**：0.64–0.73，可作为主配对指标。
- 换序鲁棒性、缺证拒答、闭合率三项已经能稳定区分系统，建议作为主指标组。

## 限制
- n=10，仅描述性；未做 NHST。
- 只有 2 个 7–9B 本地模型；gemma2 未跑。
- revised 的改动集中在可闭合字段；closure 的优势需要更独立的修订来验证。
- llama guided 的格式失败需要一个专门的 prompt-robustness 小节，不能混入能力比较。



## 关键补测：不可由闭合恢复的修订（revised_hard）

为排除“closure 只是重算了我们改的字段”这一循环，新增 wicket_transfer：
把 1 个 wicket 从一名投手转给同队另一名投手。队伍总分、extras、失分、闭合约束全部不变，
只有投手 figures 变化——**闭合规则无法恢复，必须重新读文本**。

| model | system | hard changed acc | hard stale rate |
|---|---|---:|---:|
| llama3.1:8b | direct | 0.529 | 0.000 |
| llama3.1:8b | closure | **0.529** | 0.000 |
| qwen2.5:7b | direct | 0.529 | 0.000 |
| qwen2.5:7b | closure | **0.529** | 0.000 |

**结论：closure 的全部优势都来自“可闭合字段”的自动重算；对必须重新抽取的事实零提升。**
当前方法应定位为「一致性修复层（consistency repairer）」，而不是「状态跟踪器（state tracker）」。

这直接决定 RQ3 的写法：
- 要么把方法升级为事件级账本（抽取 entity→value 的版本，再映射表格），
- 要么论文主张改为“外部闭合修复能消除账目矛盾，但不能替代抽取”，并把事件账本列为未来工作。

后者仍然是有价值的诊断结论，且与 pilot 的其余发现一致。



## Oracle 证据诊断（回答“卡在定位还是聚合”）

把 commentary 缩减为“仅含被评分字段证据句”的版本，再让模型填同样的表：

| model | 全文 control | 仅证据句 oracle | 差值 |
|---|---:|---:|---:|
| llama3.1:8b | 0.738 | 0.659 | **−7.8pp** |
| qwen2.5:7b | 0.691 | 0.594 | **−9.7pp** |

去掉非证据句后准确率**下降**，不是上升。说明：
- 失败不是“找不到目标句”，长文本检索不是主瓶颈；
- 模型需要上下文来完成聚合（总分、边际、伙伴关系），而这些恰恰不在“字段证据句”里；
- 因此方法应针对**聚合与状态维护**，而不是检索压缩。
（该 oracle 过于激进，只作为下界诊断；30 场应做“证据句+邻句”版本。）
