# Shadow候选变更控制规范

## 身份规则

- R26.15不可原地修改；
- 每个shadow使用新候选名、父候选哈希、唯一假设ID和独立manifest；
- 一次shadow只验证一个主要机制；
- 题面、金标、难度机制和协议不得在同一批次同时变化。

## 建立权限

只有一个强模型家族完成有效Pilot20，并且同一注册机制至少影响4题、至少2个锚点、全部batch为`OK`且保持锚点平衡时，才允许建立shadow。此时只允许构建和本地验证，不允许晋升。

## 允许方向

| 触发 | 允许方向 | 禁止方向 |
| --- | --- | --- |
| 主指标>65% | 只加强已被正确解决的注册机制 | 全局加长度、噪声或无关冲突 |
| 相邻下降<8点 | 只修改相邻对中的上一级 | 同时重做五级 |
| 等级倒置 | 只修倒置上一级的已定位机制 | 用平均分掩盖倒置 |
| 主指标<35%或L1<60% | L1/L2只减少一个已诊断负担 | 增加任何难度或噪声 |

## 变更预算

- 每题最多新增2个决定性span；
- 插入span触及率不得超过冻结合同的2%；
- 每场被改变的基础span比例应低于1.5%，除非事前另立合同；
- 仅靠增加长度不允许；
- 原始图不得超过48条边，增强图目标上限38；
- 必须保留事实、反事实和最小证明唯一性。

若多个限制同时适用，执行更严格者。

## 本地闭环门

- 事实与反事实金标正确；
- 单一干预和countermodel传播正确；
- 注册表、作用域和规则版本正确；
- 公开表面上的证明唯一；
- 图无环、端点与关系合法；
- metadata、question-only、ID、位置、模板和语言捷径审计通过；
- 五×五锚点—等级平衡；
- 两个干净环境逐字节重建一致；
- 新零请求成本、上下文和输出容量预检通过；
- 数据卡、manifest、变更日志和暴露账本更新。

## 外测与晋升

首次外测只覆盖受影响机制的五个匹配锚点—等级单元，使用新数据身份、新run ID、新空目录和单独授权。R26.15成绩不能移植为shadow正式成绩。

晋升至少要求：

1. 两个强模型家族在未改变R26.15上同向复现触发，每家族至少2锚点；
2. 增难路径不存在L1或全局地板效应；减负路径由fresh shadow Sentinel证明地板已消除；
3. fresh shadow Sentinel和全部静态门通过；
4. 晋升后最终候选重新获得绑定其精确哈希的正式Pilot20结果；
5. 用户明确批准晋升，失败shadow保留证据但不覆盖父候选。

## 变更记录最小字段

- shadow ID、父候选和父哈希；
- 假设ID、触发Pilot20和受影响机制；
- 题/等级/锚点/字段/关系清单；
- 文件级diff和语义diff；
- 预算计算；
- 本地门结果及哈希；
- 外测授权、run ID和费用；
- 晋升/丢弃决策与批准人。
